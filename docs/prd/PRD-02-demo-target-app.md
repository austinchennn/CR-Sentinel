# PRD-02：Demo 靶场应用

> **状态：✅ 已完成** —— `services/demo-target-app`（commit `719c6d9`；网关拦截部分见 PRD-05 commit `22e5a86`）。

## 目标

搭一个"故意有业务层漏洞"的轻量 Web 应用，作为攻击剧本的靶场，同时是比赛要求的 functional demo app 的一部分。所有请求同步落日志到 CockroachDB，成为 PatrolAgentLambda 的原始输入。

## 范围

- Lambda + API Gateway 部署的最小 Web 应用
- 4 类业务端点：登录、`?id=` 查询（IDOR）、评论/留言、管理后台路径
- 请求日志同步写入 `request_logs`
- 基础前端页面（够用即可，不追求美观，重点在攻击面）

## 非目标

- 不包含黑名单拦截逻辑（见 PRD-05，靶场只负责"暴露漏洞 + 记日志"）
- 不做真实用户体系/注册流程，用预置种子账号即可

## 功能需求

1. **登录端点**：接受用户名密码，用于演示弱密码/慢速爆破场景；不需要真实鉴权强度，重点是能被"打"
2. **`?id=` 查询端点**：返回"用户资料"之类的数据，用户可以随意改 `id` 参数读到别人的数据（故意的 IDOR 漏洞）
3. **评论/留言端点**：接受任意文本，不做内容过滤，用于演示编码变形 XSS 和社工钓鱼文本场景
4. **管理后台路径**：一个真实存在但没有强防护的 `/admin` 类路径，用于演示扫描探测场景
5. 每个请求（无论成功失败）都要写一条 `request_logs` 记录：IP、方法、路径、参数、UA、状态码、耗时、user_id（如有）
6. 预置几个种子账号到 `accounts` 表，用于后续演示账号锁定处置

## 用到的 CockroachDB & AWS 工具

- **CockroachDB**：直接 SQL 写入 `request_logs`（不经过 MCP，业务应用侧的常规写入）
- **AWS**：Lambda、API Gateway

## 验收标准

- [ ] 4 类端点均可访问且行为符合"故意有漏洞"的设计
- [ ] 每次请求都能在 `request_logs` 里查到对应记录，字段完整
- [ ] 用不同 `id` 参数请求 IDOR 端点，能读到不同用户数据（验证漏洞确实存在，否则攻击剧本演不出来）
- [ ] 种子账号数据已灌入 `accounts` 表
